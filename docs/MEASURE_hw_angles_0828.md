## 왜 쟀나

HW 가 보낸 블록 명령 런타임은 관절 한계를 MJCF `actuator ctrlrange` 에서 읽어
degree 로 바꾸고 **소수 3자리로 반올림**해 프런트에 내려준다
(`runtime/robot_runtime.py` → `round(limits[0], 3)`).

우리 데이터 계약의 정본은 `configs/so101.yaml` 의 `joint range` 이고,
MJCF 의 `ctrlrange` 는 5자리로 반올림돼 있어 둘이 미세하게 다르다.

프런트가 **내려받은 최대값을 그대로 명령**하면 그 값이 우리 정규화에서 1.0 을
넘을 수 있고, 그러면 `contract.episode.validate` 가 그 에피소드를 통째로 거부한다.
가정이 아니다 — 수집분에서 `state max 1.0062` 로 이미 1건이 거부된 적이 있다
(원인은 달랐지만 실패 양상은 같다). **수집분을 통째로 버리기 전까지 드러나지 않는다.**

## 오차의 주범 분리

`--source` 와 `--decimals` 를 바꿔 원인을 나눴다.

| limit 출처 | degree 반올림 | [-1,1] 초과 최대치 |
|---|---:|---:|
| `ctrlrange` | 3자리 | 1.370e-06 |
| `ctrlrange` | 6자리 | 1.323e-06 |
| `jntrange` | 3자리 | 1.370e-06 |
| `jntrange` | 6자리 | **4.645e-09** |

**읽는 법.** `jntrange` 는 우리 config 가 생성된 바로 그 값이라 순수 부동소수점 오차만
남는다(4.6e-09). 거기에 degree 3자리 반올림을 얹으면 1.37e-06 으로 **약 300배** 커진다.
`ctrlrange` 로 바꿔도 3자리 반올림이 있는 한 값은 그대로다.

> **정정.** 리뷰 문서 초안에서 "`MujocoBackend` 가 `jnt_range` 를 쓰면 단일 출처가
> 합쳐진다"고 썼는데, **수치는 개선되지 않는다**. 3자리 반올림이 지배적이기 때문이다.
> `jnt_range` 로 바꾸는 것은 여전히 옳지만 이유는 정확도가 아니라 **출처 일원화**다.

## 한계 — 통과가 무엇을 뜻하지 않는가

1. **규격이 일치한다는 뜻이 아니다.** 허용오차가 막아준 것이다.
   `validate(strict_range=...)` 의 허용오차를 0 으로 조이면 `elbow_flex`·`wrist_roll`·
   `gripper` 의 경계값 에피소드가 **전부 거부**된다.
2. **로봇팔은 변형 예정이다.** 관절 범위가 바뀌면 이 수치는 무효다. 변형 후 재측정 대상.
3. **실물 서보는 포함되지 않았다.** 여기서 잰 것은 숫자의 왕복이지 서보가 실제로
   그 각도에 서는지가 아니다. 실물 엔코더 값이 범위를 넘는 문제(계약 미확정 3건 중 하나)는
   이 측정과 별개다.
4. 실행이 git 체크아웃 밖이라 `EXP_LOG` 기록이 없다. 아래 명령으로 로컬에서 남길 것.

## 재현

```bash
conda activate aiot_ai
cd AI
python tools/check_angle_contract.py --log            # 기본: ctrlrange, 3자리
python tools/check_angle_contract.py --source jntrange --decimals 6
```

종료코드 1 = degree 명령이 에피소드를 무효화할 수 있다.
