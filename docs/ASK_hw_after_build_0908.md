# HW 요청 — 실물 제작 완료 시점에 받아야 하는 값 (2026-09-08)

- 수신 HW 김현석 · 발신 김준태(AI 트랙B) · 이슈 S15P21A103-30 · S15P21A103-42 · S15P21A103-113

## A. 지금 막고 있는 것 (최우선 3개)

### A-1. 자유도 — 팔 관절이 5개인가 6개인가 ⚠️ 최우선

기획서는 "범용 6축" 이고, AI 가 쓰는 실측 하드웨어 값은 **5관절 + 그리퍼** 다.

```
현행 configs/so101.yaml
  dof: 6   →  shoulder_pan · shoulder_lift · elbow_flex · wrist_flex · wrist_roll · gripper
             즉 팔 5축 + 그리퍼 1
기획서       "범용 6축"  →  팔 6축이면 총 7 자유도가 된다
```

**완료 기준**: 조립된 팔의 **서보 개수**와 각 서보의 역할 이름.
그리퍼 서보를 포함해서 몇 개인지 숫자로.

**이게 막고 있는 것**: 데이터 계약의 `action (6,)` 차원 자체. 팔이 6축이면
`(7,)` 이 되고 **지금까지 수집한 시뮬 98편과 학습된 체크포인트 전부가 무효**다.
그리고 "사람 손 궤적을 로봇이 재현 못 하는 비율" 계산이 이 값에 통째로 의존한다.

---

### A-2. 관절별 속도·가속도·명령 한계

`configs/so101.yaml` 에 이 값이 **하나도 없다** (확인함).
그래서 UMI 시연의 실행가능성 검사에서 다음이 판정 불가 상태다.

```
geometric feasibility  : 평가 가능   (자세가 도달 범위 안인가)
kinematic continuity   : 평가 가능   (프레임 간 관절 이동이 연속인가)
dynamic feasibility    : NOT_EVALUABLE   ← 이 값이 없어서
```

**완료 기준** — 관절 6개 각각에 대해:

| 항목 | 단위 | 비고 |
|---|---|---|
| 최대 각속도 | rad/s 또는 °/s | 무부하 기준인지 부하 기준인지 병기 |
| 최대 각가속도 | rad/s² 또는 °/s² | 미측정이면 "미측정" |
| 명령 갱신 최대 주기 | Hz | 우리는 30Hz 를 가정하고 있다 |
| 토크 한계 | N·m | 시뮬은 forcerange ±3.35 N·m 를 쓴다 |
| 과열·과전류 컷오프 | 있음/없음 | 있으면 조건 |

데이터시트 값이면 🔵(문서), 실측이면 🟢 로 구분해서 알려 달라. **둘은 다르다.**

**이게 막고 있는 것**: 사람 손 궤적은 로봇보다 빠르다. 우리 UMI 실측에서
선속도 최대 31.9cm/s · 각속도 최대 53.6°/s 가 나왔다. 이 값과 비교할 상대가 없다.

---

### A-3. URDF/MJCF 정본과 파일 해시

AI 시뮬이 include 하는 파일:

```
third_party/so101_mujoco/SO101/so101_new_calib.xml   (+ assets/*.stl)
```

**완료 기준** 세 가지:

1. 실물이 이 파일과 **같은 형상인가**? 다르면 실물에 맞는 파일을 주거나 무엇을 바꿨는지
2. 상류에 `so101_old_calib.xml` 과 `so101_new_calib.xml` 이 있는데 **new 가 맞는가**
3. 프린트·조립 과정에서 STL 을 수정했다면 **어느 파일을 어떻게** 바꿨는지

**왜 해시까지 필요한가**: 이 파일이 AI 의 코드 서명(`code_sha`)에 **안 들어간다**
(확인함 — 저장소 루트에 있어서 해싱 범위 밖이다). 즉 누가 조용히 교체하면
교체 전후 측정값이 **같은 서명을 달고 나란히 눕는다.** 그러면 어느 로봇으로
잰 수치인지 사후에 구분할 수 없다. 이건 AI 쪽에서 고칠 예정이고,
그 전에 **지금 파일이 실물과 맞는지**만 확인해 주면 된다.

## B. 계약·데이터 유효성 (4개)

### B-1. 조립된 로봇의 관절 범위 실측 + 영점 정의

AI 가 쓰는 값 (config, `calibration: new_calib`, 관절 중앙 = 0):

```
shoulder_pan   [-1.9199,  1.9199] rad   (±110.0°)
shoulder_lift  [-1.7453,  1.7453]       (±100.0°)
elbow_flex     [-1.6900,  1.6900]       (± 96.8°)
wrist_flex     [-1.6581,  1.6581]       (± 95.0°)
wrist_roll     [-2.7438,  2.8412]       (-157.2° ~ 162.8°)
gripper        [-0.1745,  1.7453]       (-10.0° ~ 100.0°, 하한이 닫힘)
```

**완료 기준**: 관절별 실제 도달 가능 최소·최대 각도, 그리고 **0 이 어디인가**.
서보 혼(horn) 장착 각도가 한 칸 틀어지면 영점이 통째로 밀린다.

**왜 중요한가**: AI 계약이 이 범위로 [-1,1] 정규화한다
(`x_norm = 2(x-lo)/(hi-lo) - 1`). 범위가 다르면 **같은 정규화값이 다른 각도**가 되고,
학습한 정책이 실물에서 엉뚱한 데로 간다. 조용히 틀리는 종류의 오류다.

---

### B-2. 그리퍼 — 명령값 ↔ 손가락 간격 곡선

AI 가 현재 쓰는 값:

```
open_cmd  0.60  →  gap 4.86cm  (시뮬 계산값)
close_cmd 0.06  →  gap 약 1.8cm
닫힘 시 간격 약 1.7cm  →  대상물 1.5~2.5cm 로 스코프 확정
```

**완료 기준**: 실물에서 명령값 몇 점에 대한 **실측 간격**. 최소 5점.

| 명령 (정규화 또는 rad) | 실측 손가락 간격 (mm) | 측정 지점 |
|---|---|---|
| 완전 닫힘 | ? | 팁 / 패드 중앙 중 어디를 쟀는지 |
| … | ? | |
| 완전 열림 | ? | |

**측정 지점을 반드시 병기해 달라** — 팁 간격과 패드 간격이 다르고, UMI 핸드헬드
캘리브레이션(0~90mm)과 공식 MJCF 팁 간격(4.1~133.4mm)이 이미 안 맞아서
어느 지점을 쟀는지 몰라 막혀 있다 (LIMITS L53).

**추가**: 그리퍼 모델링을 바꿀 예정이라고 들었다. **이 값이 최종본인가?**
아니면 이 요청은 최종본 나온 뒤로 미루는 게 맞다 — 바뀌면 다시 재야 하는 값이다.

---

### B-3. 카메라 → 손끝 거리 (LIMITS L60, 숫자 하나)

UMI 핸드헬드 핑거가 SO-101 의 **50% 축소**다 (MW 확인 🔵).
UMI 가 캘리브레이션 없이 성립하는 근거는 **손목 카메라에 찍히는 핑거의
겉보기 크기가 일치**하는 것이다. 즉 카메라→핑거끝 거리도 절반이어야 상쇄된다.

**완료 기준**: 로봇의 **손목 카메라 렌즈 중심 → 핑거 끝** 거리 1개 (mm).

MW 가 핸드헬드 쪽 값을 주면 비를 계산한다. **비가 0.5 에서 멀면 학습 후
실물에서만 드러나는 실패**다 — 시뮬에서는 절대 안 보인다.

---

### B-4. 카메라 마운트 기하와 반복성

**완료 기준**:

1. **정면 카메라**: 로봇 베이스 기준 위치(x,y,z)와 바라보는 방향. 대략값도 도움된다
2. **손목 카메라**: 어느 링크에 붙었고, 그 링크 기준 위치·자세
3. **탈착 반복성**: 카메라를 떼고 다시 붙이면 **같은 자리인가**. 나사 구멍이
   위치를 정하는가, 아니면 매번 다른가
4. 렌즈 사양 (화각). MW 회신으로 "초광각 아니라 광각, 왜곡계수 없음" 🔵 은 받았다

**왜 3번이 중요한가**: hand-eye 오차는 **상수 편향**이라 학습이 지우지 못한다.
랜덤 노이즈는 평균으로 지워지지만 상수 편향은 궤적 전체를 민다.
시뮬 실측 🟢 — **±10mm 에서 재생 성공률이 4/4 → 3/4 로 떨어진다.**
카메라가 매번 다른 자리에 붙으면 그 편향이 매 세션 달라지고, 그건 학습으로 못 덮는다.

## C. AI 가 직접 재는 것 — HW 는 장비 접근만 (3개)

계측기는 AI 가 만든다. HW 에 필요한 건 **로봇을 쓸 수 있는 시간과 안전 감독**이다.

### C-1. 반복도 (repeatability) ⚠️ 가장 무서운 값

같은 관절 명령을 N 회 반복했을 때 손끝이 실제로 오는 위치의 산포.

**왜 이게 가장 무서운가**: 시뮬 실측 🟢 재생 위치 허용오차가
**±5mm 에서 4/4 · ±10mm 에서 3/4 · ±15mm 에서 1/4** 다.
실물 반복도가 10mm 보다 나쁘면 **재생 기반 접근 자체가 성립하지 않는다.**
그러면 태스크 설계나 대상물 크기를 다시 정해야 하고, 그건 지금 알아야 하는 일이다.

**필요한 것**: 로봇 + 손끝 위치를 재는 방법 (다이얼 게이지, 자, 사진 기준점 등
HW 가 편한 방법). 3개 자세 × 10회면 첫 숫자가 나온다.

### C-2. 추종 오차 — 명령 각도 vs 실제 각도

시뮬에서 이 값이 관절별로 이미 있다 🟢 (명령−측정, `action − state`):

```
shoulder_pan 0.053° · lift 0.278° · elbow 0.385° · wrist_flex 0.857° · gripper 1.593°
```

**실물에서 이 표를 다시 채우는 것이 첫 sim2real 숫자가 된다.**
필요한 것: 관절 각도 피드백을 읽는 방법 (서보가 현재 각도를 돌려주는가).

### C-3. 개루프 그림자 재생 (shadow rollout) — 안전 조건부

시뮬에서 기록한 에피소드 1편의 **관절 명령을 실물에 그대로 재생**하고
손끝이 어디로 가는지 본다. 정책은 안 돌린다.

**안전 조건 (AI 가 먼저 지킨다)**:

```
1차: 물체 없음 · 저속(정상 속도의 25% 이하) · 사람이 비상정지에 손 올린 상태
2차: 물체 있음 · 저속
3차: 정상 속도
```

Safety Controller (ROS 소관) 가 붙기 전에는 **1차만** 한다.
필요한 것: 비상정지 수단, 그리고 저속 실행이 가능한가.

## D. 지금은 요청하지 않는 것

문서만 늘어나는 걸 피하려고 뺐다. 필요해지면 그때 묻는다.

| 항목 | 왜 지금 아닌가 |
|---|---|
| 정확한 질량·관성 텐서 | 시뮬 0.632kg 로 충분히 돌고 있다. 실물 동역학을 맞출 단계가 아니다 |
| 링크 길이 mm 단위 실측 | B-1(관절 범위)과 C-1(반복도)이 먼저다. 그 결과가 나쁘면 그때 링크로 내려간다 |
| 최대 페이로드 | 대상물 20g 이다. 여유가 압도적이라 지금 병목이 아니다 |
| Jetson 관련 | 별도 이슈 42. 다만 **Orin Nano 4GB 인가 8GB 인가**는 아직 미확인이다 |

## E. 우선순위 한 줄 요약

```
오늘 답이 필요한 것    A-1 (서보 개수)  ← 이게 6이 아니면 계약이 바뀐다
이번 주               A-2 (속도·가속도)  A-3 (URDF 정본)  B-1 (관절 범위·영점)
그리퍼 확정 후        B-2 (gap 곡선)  B-3 (카메라→핑거끝)
장비 시간 잡히면      C-1 (반복도)  ← 나쁘면 태스크 설계를 다시 해야 한다
```

**A-1 하나만 먼저 답해 줘도 된다.** 나머지는 순차로 받는다.
