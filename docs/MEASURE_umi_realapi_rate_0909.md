# MEASURE — 실물 실행 API 의 waypoint 주기 예산 (2026-09-09)

계측기 `tools/umi_rate_budget.py` · 재현: `python3 tools/umi_rate_budget.py`
작성 김준태(트랙 B) · 상수 출처는 `so101_direct_motor_pipeline` 원본 코드 🔵,
속도 통계는 실측 🟢

> **이 문서가 답하는 질문.** "1.16Hz 문제"가 정확히 무엇인가.
> 시뮬·정책 대화가 물었고 추측하지 말라고 했다.

## 0. 결론 먼저

**추론 주기 얘기가 아니다.** 실물 API `validate_trajectory` 의 **가속 검사를
통과하는 waypoint 최소 간격**이다. 계약 30Hz 와는 다른 축이므로
"26배 차이"로 읽으면 안 된다.

제약이 두 개다.

| | 종류 | 값 | 함의 |
|---|---|---|---|
| A | 명시 | `0.05 <= dt <= 60` (`core/models.py`) | waypoint 간격 상한 20Hz. 계약 30Hz 와 이미 충돌 |
| B | 암묵 | `5.774 * dq / dt**2 <= max_accel(3.0)` | **아래가 본론** |

## 1. B 가 왜 구조적 문제인가

`5.774 = 10/sqrt(3)` 는 **정지→정지 quintic** 의 피크 가속 계수다.
연속 궤적에서는 `dq = v*dt` 이므로 검사값이

```
5.774 * (v*dt) / dt^2  =  5.774 * v / dt
```

가 된다. 분모에 `dt` 가 남는다. 즉 **waypoint 를 촘촘하게 넣을수록 검사값이 커진다.**

```
                             v=0.4473 (내 평균)      v=0.5333 (속도한계 준수)
 30Hz dt=0.0333s     77.48 rad/s^2 =  25.8x       92.38 rad/s^2 =  30.8x
 20Hz dt=0.0500s     51.65 rad/s^2 =  17.2x       61.59 rad/s^2 =  20.5x
 10Hz dt=0.1000s     25.83 rad/s^2 =   8.6x       30.79 rad/s^2 =  10.3x
  5Hz dt=0.2000s     12.91 rad/s^2 =   4.3x       15.40 rad/s^2 =   5.1x
  2Hz dt=0.5000s      5.17 rad/s^2 =   1.7x        6.16 rad/s^2 =   2.1x
  1Hz dt=1.0000s      2.58 rad/s^2 =   0.9x        3.08 rad/s^2 =   1.0x
```

## 2. 어느 속도 통계를 쓰느냐로 요구 간격이 갈린다

| 속도 출처 | v [rad/s] | 필요 dt | = Hz | 구속 |
|---|---|---|---|---|
| 내 평균 (19편, `mean|action-state|`) 🟢 | 0.4473 | 0.861s | 1.16Hz | 가속 |
| 시뮬·정책 p99 (98편 wrist_flex) 🟢 | 1.3600 | 2.618s | 0.38Hz | 가속 (속도도 위반) |
| 시뮬·정책 최대 (98편 wrist_flex) 🟢 | 1.3630 | 2.623s | 0.38Hz | 가속 (속도도 위반) |
| 속도한계 딱 지킨 quintic 상한 `V/1.875` | 0.5333 | 1.026s | 0.97Hz | 가속 |

**마지막 줄이 핵심이다.** 시연을 속도 한계까지 느리게 해도 `dt >= 1.026s` 가 남는다.
정책 주기를 낮춰도, 시연을 느리게 해도 해결되지 않는다.
근본 원인은 **연속 궤적에 정지→정지 모델을 적용하는 검사식**이다.

## 3. 그리퍼는 다르다 — 램프로 해결된다

스텝 명령으로 `gap` 을 한 번에 닫으면 0.8771 m/s 🟢 vs 한계 0.08 m/s.
그러나 램프로 펴면 통과한다 — `close_s 1.0s = 30틱`, 필요한 것은 19틱.
즉 **팔과 그리퍼는 원인이 다르다.** 그리퍼는 파라미터로, 팔은 인터페이스로 풀린다.

## 4. 선택지 — 셋 다 우리 결정이 아니다

| | 방안 | 대가 |
|---|---|---|
| a | 실행측이 궤적 전체를 하나의 profile 로 받아 내부 보간, 검사를 궤적 단위로 | MW/HW 작업 |
| b | 연속 구간에 `5.774` 대신 실제 2차 차분을 쓰도록 검사 수정 | 검사가 느슨해지는 위험 |
| c | waypoint 를 1Hz 급으로 희소화 | 정책 출력 대부분을 버린다 |

**리샘플러는 HW/MW 회신 전에 확정하지 않는다.** (a) 또는 (b) 가 되면
리샘플러는 필요 없거나 완전히 다른 모양이 된다.

## 5. 내 오류 정정 2건 — 덮지 않는다

**정정 1 (통계 선택).** 최초 보고에서 "실물 속도 한계는 통과한다"고 썼다.
**평균을 썼다.** 한계 검사는 최대/p99 로 판정한다. 시뮬·정책의
`check_real_limits` 는 wrist_flex 최대 1.3630 / p99 1.3600 vs 한계 1.0,
**3430/13818 = 24.8% 스텝 위반**을 냈다. 평균으로는 이 24.8% 가 보이지 않는다.
평균으로 한계를 판정하면 안 된다.

**정정 2 (라벨 불일치).** 0909 전달문의 §1 표를 `v=0.4473 기준`이라고 적었는데
실제 숫자는 `v=0.5333` 열이었다 (30Hz 92.38 = 30.8x). 올바른 값은
`v=0.4473` 에서 **77.48 = 25.8x** 다. 결론(전 구간 초과)은 바뀌지 않지만
숫자와 라벨이 어긋난 것은 그 자체로 오류다.
`umi_rate_budget.py` 가 이제 **두 열을 항상 같이 출력**한다 — 한 열만 내면
같은 실수가 반복된다. 계측기를 고쳐서 막았다.

## 6. 이 문서가 못 말하는 것

- 실행 API 원본을 내가 실행해 본 것이 아니다. 상수는 **코드 읽기** 🔵 다.
  `dt`·`max_accel`·`5.774` 가 실제 배포 버전에서 같은지 HW 확인 필요
- 내 v 는 19편 시뮬 유래 UMI 변환 데이터다. **사람 손 시연의 실제 속도가 아니다.**
  UMI 실기록이 오면 다시 재야 한다 — 사람 손은 더 빠를 가능성이 높다
- (a)/(b)/(c) 중 무엇이 되든 그 뒤 궤적 추종 오차(`tracking_rad 0.08`)는
  별도 계측 대상이다. 여기서 다루지 않았다
