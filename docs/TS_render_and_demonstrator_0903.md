# TS · 렌더 비결정성과 시연자 갈라짐 (2026-09-03)

작성: 김준태(트랙B) · 관련 이슈 S15P21A103-34, -35, -64
상태: 3건 모두 수정 완료. 4번째(dwell)는 재측정 대기.

셋 다 **"어제 통과했던 계측이 오늘 다른 답을 내는"** 종류다. 세 건이 겹쳐 있어서
성공률 5.7% 를 하루 동안 믿을 수 없었다.

## 1. 같은 명령이 다른 성공률을 냈다 → MSAA

**증상** 같은 체크포인트, 같은 시드 블록 3000~3099, 같은 설정으로 세 번 돌려
**11 / 10 / 7** 이 나왔다.

**어떻게 좁혔나 (1) — 기준선을 먼저 봤다**

성공률만 보면 "학습 분산인가" 로 넘어갔을 것이다. 그런데 같은 출력에 baseline 셋이
같이 찍힌다.

```
hold      0/100  0/100  0/100
zero      0/100  0/100  0/100
scripted 84/100 84/100 84/100   ← 실패 형태 통계까지 소수점 단위로 동일
bc       11/100 10/100  7/100   ← 이것만 흔들린다
```

**이미지를 읽지 않는 정책 셋은 완전히 재현되고, 읽는 하나만 흔들린다.**
씬·물리·시드·성공판정은 결정적이라는 뜻이고, 원인은 이미지 경로로 좁혀졌다.
baseline 이 계측기의 영점 역할을 한 것이다.

**어떻게 좁혔나 (2) — 세 고리를 따로 찔렀다**

`eval/determinism.py` 를 만들어 R(렌더)·P(추론)·E(롤아웃)을 분리했다.
허용 오차를 두지 않았다 — 오차를 두면 재려는 효과가 그 안에 숨는다.

```
R 한 프로세스 재렌더   해시 다름   최대 픽셀차 1.0 계조
R 새 env 같은 시드     해시 다름   최대 픽셀차 1.0 계조
P 같은 관측 두 번      최대 절대차 0.000e+00  ← 추론은 결정적
E 같은 시드 두 번      성공 True 161틱 / 성공 False 200틱, 닫은틱 74 / 37
```

**1/255 픽셀 차이가 성공/실패를 뒤집고 그리퍼 닫는 시점을 74틱 → 37틱으로 옮긴다.**

**어떻게 좁혔나 (3) — 원인 후보를 하나 껐다**

MSAA(멀티샘플링)는 GPU 오프스크린 렌더의 대표적 비결정 원인이다 🔵.
MuJoCo 기본값 `offsamples=4`. 설정으로 노출해 0 으로 껐다.

```
offsamples 4 → R 다름(1계조), E 다름
offsamples 0 → R 비트 동일, E 동일 (77/77틱, 3.82/3.82mm)
```

**조치** `cameras.offsamples: 0`. EGL 그대로 쓴다 (osmesa 불필요 — 100편 평가에
시간 단위가 걸린다). LIMITS **L37 해소**.

**남은 것 — 이건 고쳐지지 않았다** 하니스는 결정적이 됐지만 **정책이 1계조에 뒤집힌다**는
사실은 그대로다. 실물 카메라 노이즈는 1계조보다 훨씬 크다. **LIMITS L39 신규.**
계측기를 고치려다 실물 전이의 조기 경보를 얻었고, 그 결과가 나쁘다.

**일반화** 재현성 문제를 만나면 **정답을 아는 기준선이 같이 재현되는지 먼저 본다.**
그 대조가 없었으면 학습 분산으로 오진했을 것이다.

## 2. 상한선이 데이터를 만든 시연자와 달랐다 → 계획이 두 곳에 복제

**증상** dwell 을 넣으려고 `ScriptedPickPolicy._build_plan` 을 고쳤는데
**수집 데이터의 `n_steps` 가 141 에서 안 바뀌었다.**

**어떻게 좁혔나** `data/collect.py` 를 열어보니 **파지 계획이 하나 더 있었다.**
같은 웨이포인트를 두 곳이 각자 갖고 있었고, 뒤 구간이 달랐다.

```
data/collect.py            36 + 30 + 30 + 45         = 141틱
policy/baselines.py        36 + 30 + 30 + 45 + 24    = 165틱
```

즉 **`scripted 84%` 라는 상한선이 데이터를 만든 시연자와 같은 것이 아니었다.**
어느 한쪽 수치만 봐서는 절대 드러나지 않는다 — 둘을 나란히 세울 이유가 없었으니까.
드러난 것은 한쪽을 고쳤는데 다른 쪽이 안 움직였기 때문이다.

**조치** `sim/mujoco/kinematics.py: pick_waypoints` 로 정의를 하나로 합쳤다.
구간 타이밍도 코드에서 `configs/so101.yaml grasp.timing` 으로 옮겼다 —
시연자 변경이 `config_sha` 에 남는다. 검증: 수집·평가 모두 dwell 0 에서 141틱,
dwell 0.5 에서 156틱 일치.

**영향 범위 미확정** 165틱 baseline 으로 측정한 이전 `scripted` 수치(84%, 닫는 순간
4.7mm)가 141틱 시연자와 얼마나 다른지는 **재측정으로만 알 수 있다.**
평가의 `act` 가 계획 끝에서 마지막 행동을 유지하므로 뒤 24틱은 무해할 것으로
**추정**하지만 🟡, 추정을 결과로 쓰지 않는다. v4 실행의 `scripted` 값을 확인해야 한다.

**일반화** 같은 것을 두 곳에서 정의하면 갈라지고, **갈라진 것은 한쪽만 고칠 때 드러난다.**
정의가 하나뿐인지 확인하는 것이 계측기 검증의 일부다.

## 3. 읽는 규칙이 정답을 아는 기준선을 오분류했다 → 지연은 판정 근거가 아니다

**증상** 닫는 순간 계측기의 첫 읽는 규칙은
`최근접 대비 지연 > 5틱 → 타이밍 문제` 였다.

**어떻게 좁혔나** 같은 지표를 `scripted` 에도 찍었다.

```
scripted  지연 +30틱 (>5틱 100%)  →  84% 성공
bc        지연 +17틱 (>5틱  61%)  →   7% 성공
```

**지연이 더 큰 쪽이 더 성공한다.** 규칙이 맞다면 scripted 를 타이밍 문제로
오분류했어야 한다. 규칙이 틀렸다.

원인: 최근접 시점을 "닫아야 할 시점"으로 잘못 잡았다. 실제로 최근접 시점은
**접근 완료 시점**이고 그 뒤 수십 틱은 하강·정렬 후 닫는 **정상 시퀀스**다.
차이는 그 사이에 거리를 **유지하는가 발산하는가**다 — scripted 0.3 → 4.7mm,
bc 5.1 → 14.0mm.

**조치** 판정을 **닫는 순간의 절대 거리**로 옮겼다. 지연은 참고값으로만 출력하고
"지연은 판정 근거가 아니다"를 함께 찍는다. 최근접 대비 증가량도 같이 출력한다.

**부산물** "데이터가 고정 틱에 닫으라고 가르쳤다"는 어시스턴트 가설도 지연 수치로는
지지되지 않았다. 코드를 읽고 나서야 진짜 결함(도착 후 머무는 프레임이 0개)이 나왔다.
**가설을 세운 뒤 코드를 읽지 않은 것이 오류의 원인이다.**

**일반화** 새 지표는 **`scripted` 에서 먼저 읽고, 읽는 규칙이 그것을 옳게 분류하는지
확인한 뒤** `bc` 에 적용한다. 정답을 아는 기준선이 있는데 안 쓰는 것이 반복 오류다.

## 4. `--check` 가 통과했는데 낡아 있었다 (같은 날, 기록 도구)

**증상** `tools/update_readme.py --check` 가 "일치한다"를 반환했다.

**어떻게 드러났나** 로컬 `EXP_LOG.jsonl` 55줄, 서버 61줄. **양쪽이 같이 낡아서**
README 와 EXP_LOG 가 일치했다. 가드가 엉뚱한 이음매를 지키고 있었다.

**조치** 생성 블록에 로그 기록 수·리비전·현재 HEAD 를 찍고, 최신 기록의 리비전이
HEAD 와 다르면 `--check` 를 실패시킨다. 지금 README 는 스스로
**"이 수치들은 현재 코드에서 나온 것이 아니다"** 라고 말한다.

**일반화** 일치는 최신성이 아니다. 대조 도구는 **자기가 읽는 입력이 최신인지**도 봐야 한다.
