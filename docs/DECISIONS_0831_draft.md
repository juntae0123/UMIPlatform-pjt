## D-AI-11 · 도메인은 "소형 부품 취급", 제품은 "스킬 전환 플랫폼"

- 작성자: 김준태 (트랙 B) · 2026-08-31 · 계기: 전문가 리뷰 E3
- **상대 트랙 영향: 있음 — PM·FE·BE 전부**

**결정.** 도메인을 고객군이 아니라 **작업의 모양**으로 정의한다 —
`1.5~2.5cm 물체를 · 15×35cm 안에서 · ±10mm 정밀도로 · 집어서 옮긴다`.
고객마다 작업 내용이 달라도 이 모양이 같으면 하나의 도메인이다.
제품 가치는 **여러 스킬을 클릭으로 전환**하는 것이다.

**왜.** ① 작업이 다 똑같으면 스크립트로 충분하고 학습이 필요 없다.
**모양은 같고 내용은 다른 것**이 학습이 이기는 유일한 지점이다.
② 물리 제약이 이미 이 모양을 강제하고 있다 🟢. 취향이 아니다.
③ 타겟은 "앞 공정이 사람인 자리" — 사람이 물체를 놓으면 위치가 매번 달라지고,
그 지점에서 재생 방식이 무너진다는 것을 실측했다 (±15mm 1/4, ±50mm 0/4) 🟢.

**되돌릴 조건.** 후보 도메인의 실제 대상물이 이 물리 범위에 들어오지 않는 것이 확인되면
(LIMITS L14), 모양 정의 자체를 다시 잡는다.

## D-AI-12 · 스킬은 학습 정책과 스크립트를 섞는다. 개수 제한은 두지 않는다

- 작성자: 김준태 (트랙 B) · **어시스턴트 제안(학습 스킬 2개 제한)을 사용자가 기각** → `REJECTED.md` R-AI-6

**결정.**
- 스킬을 등록할 때 그 작업의 **위치 변주 폭을 측정**한다. ±10mm 안이면 `scripted`, 넘으면 `learned`
- `Policy` 프로토콜이 둘을 구분하지 않고 롤아웃 harness 가 같은 조건으로 채점한다 🟢 —
  플랫폼은 어느 쪽인지 알 필요가 없다
- 학습 정책은 **스킬별 독립 체크포인트**로 둔다 (단일 멀티태스크 모델은 기각, `REJECTED.md` R-AI-5)
- **학습 스킬 최소 1개는 필수.** 그 하나는 replay 와 나란히 세워 이겨야 한다

**왜 개수 제한이 없어졌나.** 제한의 전제가 "모든 스킬이 학습 정책"이었고 그게 틀렸다.
스크립트 스킬은 사실상 공짜다 — 우리 `ScriptedPickPolicy` 가 이미 20회 중 19회 = 95% 다 🟢.
그리고 시뮬에서는 스크립트 수집에 **사람 시간이 0** 이라 학습 스킬 개수 제한도 완화된다.

**왜 학습 스킬 1개는 못 빠지나.** 스크립트만 N개면 심사에서
"티칭 펜던트와 뭐가 다른가"가 나오고 기술 주장 전체가 무너진다.
데모의 필수 장면은 이것 하나다 — **물체를 손으로 5cm 옮긴다 → 재생 스킬 실패, 학습 스킬 성공.**

**스키마 영향 (BE 이슈 18·19 정정 필요).**
```sql
ALTER TABLE skill ADD COLUMN policy_kind TEXT NOT NULL
  CHECK (policy_kind IN ('learned','scripted'));
ALTER TABLE skill ADD COLUMN position_variation_mm REAL;   -- 측정값. 10 초과면 learned 필수

-- 로봇 1대에 스킬마다 배포가 하나씩 동시에 올라간다
ALTER TABLE deployment ADD COLUMN skill_id BIGINT NOT NULL REFERENCES skill(id);
DROP INDEX  <기존 (robot_id) WHERE status='active'>;
CREATE UNIQUE INDEX ON deployment (robot_id, skill_id) WHERE status = 'active';
```
`docs/PROPOSAL_schema_api_0828.md` 의 유니크 인덱스 제안은 **틀렸다**. 위 정정이 정본이다.

**계약 영향 (트랙 A 합의 필요, 최우선).** 에피소드 메타에 `skill` 필드가 **필수**가 된다.
스킬 없이 저장된 에피소드는 어느 정책의 데이터인지 알 수 없다.
D-AI-10 에서 "있으면 좋다"였던 것이 제품의 근간으로 올라갔다.

**되돌릴 조건.** 스킬 수가 늘어 스킬당 수집 비용이 병목이 되면 멀티태스크 모델을 재검토(R-AI-5).

## D-AI-13 · 양팔·다른 구조는 별도 계약·별도 로봇으로 등록한다. 구조 확장 데모까지만 주장한다

- 작성자: 김준태 (트랙 B) · **상대 트랙 영향: 있음 — 계약 버전, FE 로봇 등록**

**결정.**
- 양팔 시뮬은 **계약을 바꾸는 것이 아니라 계약을 하나 더 만드는 것**이다.
  `state (6,) → (12,)`, `action (6,) → (12,)` 이므로 새 `contract_version` 과 새 `robot` 레코드를 만든다.
  단일팔 데이터·정책은 그대로 유효하고, 체크포인트 로드 시 계약 버전 대조가 이미 있어서 섞이지 않는다 🟢
- 시연에서 **학습 성공률은 주장하지 않는다.** 스크립트 구동 + "같은 파이프라인이 이 구조도 등록·구동한다"까지만
- 무대에서 **"이건 시뮬이고 학습 정책은 단일팔입니다"를 먼저 말한다**

**왜 가능한가.** 우리 씬은 공식 MJCF 를 include 하고 config 로 주입하는 구조라 🟢
MJCF 를 두 번 include 하고 위치를 다르게 주면 양팔 씬이 된다. 공식 MJCF 는 수정하지 않는다.

**왜 학습은 주장하지 않는가.** 양팔 협조 태스크는 단일팔보다 난이도가 크게 높고 🟡,
6주 안에 게이트를 통과시킬 근거가 없다. **못 잰 것을 됐다고 말하지 않는다.**

**이 결정이 주는 것.** 플랫폼 주장이 강해진다 —
"로봇 구조가 바뀌어도 같은 파이프라인이 돈다"가 URDF 등록(FE)과 계약 버전 대조로 증명된다.
"우리는 팔을 안 판다, 방법을 판다"는 포지션과 정확히 맞물린다.

**되돌릴 조건.** 단일팔 학습 스킬이 게이트를 통과하고 시간이 남으면 양팔 학습을 Stretch 로 올린다.
