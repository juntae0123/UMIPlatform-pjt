## Keep — 유지할 것

### 계측기를 결과보다 먼저 의심했다

자기 계측 결함 **5건**을 찾아 고쳤다. 중요한 건 **전부 낙관적 방향으로 편향**돼 있었다는 점이다.

| 결함 | 영향 |
|---|---|
| 관절한계 판정이 클립 **뒤에** 있어 `within_limits` 가 항상 True | 파지 ±100mm 90%→**65%**, 도달성 66.7%→**63.9%** |
| `np.isclose` 기본 `rtol=1e-5` 가 오차를 통과 | 2.8e-5 rad 를 못 걸러내고 있었다 |
| 조건별로 시드가 달랐다 | 비교가 성립하지 않았다 → 전부 seed 0 재실행 |
| `lift_height_m: 0.12` 가 도달 불가능 | 관절한계에 클램프된 자세로 성공 판정 → **0.08** 로 정정 |
| EXP_LOG 가 git 정보를 조용히 잃음 | 모든 기록 `git_rev=unknown` → `code_sha` 추가 |

같은 방향인 게 우연이 아니다. **검사를 느슨하게 만드는 실수는 통과를 만들어서 눈에 안 띄고,
반대 방향 실수는 바로 실패로 드러나 그 자리에서 고쳐진다. 살아남는 버그가 낙관적인 버그다.**

수치가 내려갔지만 그게 실제 값이다. 정정 전 수치는 지우지 않고 MEASURE 문서에 정정 절로 남겼다 —
지우고 새 수치만 쓰면 같은 실수를 또 한다.

## Problem — 문제였던 것

### MR 타깃이 master 로 갔다 (오늘 가장 큰 사고)

AI 작업 12커밋이 `ai` 가 아니라 **`master` 로 머지**됐다. 그 과정에서 `origin/ai` 가 삭제되고,
`master` 가 `dev` 보다 **19커밋 앞서는 계보 역전**이 생겼다.

원인은 두 개로 본다:
1. **기본 브랜치가 `master`** → New merge request 화면의 target 이 자동으로 master
2. **Delete source branch 체크박스**가 켜진 채 머지 → 공유 브랜치 `ai` 가 삭제

유실은 없었다. 로컬에 전부 남아 있어서 `ai` 를 되살리고 `ai → dev` 로 정렬 중이다.

**우리만의 실수가 아니다.** 같은 날 다른 파트 2곳도 master 로 직행했다
(최은찬 평가자료, 김현석 보고서). 프로젝트 설정 문제다.

### EXP_LOG 가 존재 이유를 한 번도 수행하지 못했다

트래커의 목적은 "이 수치가 어느 코드에서 나왔나"를 남기는 것이다.
그런데 기록된 **모든** 실행이 `git_rev: "unknown"`, `git_dirty: false` 였다.

계측이 MuJoCo 깔린 환경(= git 체크아웃 아님)에서만 돌았고, `git status` 의 빈 출력을
`bool("")` 로 읽어 **"clean"** 으로 판정했다. `git_dirty: false` 는 깨끗하다는 뜻이 아니라
**저장소가 아니라는 뜻**이었다.

**에러가 없었다.** 필드는 채워져 있었고 값만 무의미했다.
"기록했다"는 "기록이 유용하다"와 다르다.

### 환경 차이로 재현되지 않는 버그

한글 경로(`.../특화/...`) 때문에 MuJoCo 가 씬을 못 여는 것을 **실기에서 돌려보기 전까지 몰랐다.**
리눅스에서는 한글 경로가 그냥 동작한다. `ParseXML: Error opening file` 이라 파일이 없는 것처럼 읽힌다.

**"내 환경에서는 됨" 은 검증이 아니다.**

같은 성격으로 CRLF 도 있었다. Windows 체크아웃이 줄바꿈을 바꿔서 `view.py` 190줄이
내용 변경 없이 커밋에 딸려 들어갔다. `--ignore-cr-at-eol` 로 가려내고
`.gitattributes` 로 고정했다.

### 계약 결정 3건이 6개 이슈를 막고 있다

S15P21A103-27 의 정규화 규칙 / 타임스탬프 필드 / **범위 초과값 처리**.
셋째는 아직 제안조차 없다 — 18건 중 1건에서 정규화 state 최댓값이 **1.0062** 로

실물 엔코더도 같은 값을 낸다 (백래시·캘리브 오차·역구동).

이게 28~31 · 34 · 64 를 막는다. **답이 늦어지는 만큼 6건이 같이 늦어진다.**
