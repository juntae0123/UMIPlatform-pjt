# TS — 내 계측기가 5군데 틀렸다 (2026-08-27)

- 작성자: 김준태 (트랙 B)
- 이슈: S15P21A103-60, S15P21A103-63
- 증상: 없었다. **전부 정상으로 보이는 수치를 내고 있었다**
- 결론: 5건 모두 **낙관적 방향으로** 편향돼 있었다. 이게 이 문서를 쓰는 이유다

계측기의 결함은 에러를 내지 않는다. 그냥 좋은 숫자를 준다.
그래서 "결과가 나왔다"는 것은 계측기가 맞다는 증거가 아니다.

## 왜 5건이 전부 같은 방향이었나

우연이 아니다. 계측 코드를 쓰는 사람은 **성공을 확인하려는 동기**를 갖고 있고,
검사를 느슨하게 만드는 실수는 통과를 만들어서 눈에 안 띈다. 반대 방향 실수는
바로 실패로 나타나서 그 자리에서 고쳐진다. **살아남는 버그가 낙관적인 버그다.**

## 결함 1 — 관절한계 판정이 클립 **뒤에** 있었다

`sim/mujoco/kinematics.py`. IK 반복에서 관절값을 범위로 클립한 **다음에** 범위 안인지
검사했다. 클립한 값은 당연히 범위 안이므로 `within_limits` 가 **항상 True** 였다.

```python
# 틀림 — 클립하고 나서 검사하면 언제나 통과다
q[free] = np.clip(q[free] + step, lo[free], hi[free])
within = np.all((q >= lo) & (q <= hi))     # 항상 True

# 맞음 — 클립 전에 판정한다
raw = q[free] + step
if np.any(raw < lo[free] - 1e-9) or np.any(raw > hi[free] + 1e-9):
    hit_limit = True
q[free] = np.clip(raw, lo[free], hi[free])
```

**영향 — 재측정 결과:**

| 조건 | 수정 전 | 수정 후 |
|---|---|---|
| 파지 ±60mm | 100% | **90%** |
| 파지 ±100mm | 90% | **65%** |
| 도달성 | 66.7% | **63.9%** |

어떻게 찾았나: "도달 불가가 한 번도 안 나오는데 이게 맞나"를 의심하고 판정 코드를 읽었다.
**수치가 너무 깨끗한 것이 단서였다.**

## 결함 2 — `np.isclose` 의 기본 `rtol` 이 오차를 통과시켰다

config 와 MJCF 의 관절범위를 대조하는 검사. `atol=1e-9` 만 주고 `rtol` 을 안 줬다.
기본값 `rtol=1e-5` 가 살아 있어서, 값 크기에 비례한 여유가 생겼다.

```python
np.isclose(a, b, atol=1e-9)                 # rtol=1e-5 가 기본으로 살아있다
np.isclose(a, b, rtol=0.0, atol=1e-9)       # 절대오차만 본다
```

**약 2.8e-5 rad 차이를 통과시키고 있었다** — 잡으려던 3e-6 보다 느슨하다.

어떻게 찾았나: "1e-9 이내 일치"라고 문서에 쓰면서 실제 호출을 다시 읽었다.
**문서에 적은 기준과 코드가 다른 것**이 단서였다.

## 결함 3 — 조건별로 시드가 달랐다

jitter ±30 / ±60 / ±100mm 를 각각 다른 시드로 돌려놓고 성공률을 비교했다.
**다른 물체 배치로 얻은 성공률끼리 비교하는 것은 비교가 아니다.**

조치: 전부 `seed=0` 으로 재실행. 롤아웃 harness 도 **모든 정책이 같은 시드**를 보도록 고정했다
(`eval/rollout.py` 의 `evaluate`).

## 결함 4 — 들어올림 목표 높이가 애초에 도달 불가능했다

`configs/so101.yaml` 의 `lift_height_m: 0.12`. 손가락을 수직으로 유지한 채로는 못 간다.

| 파지점 위 높이 | 위치오차 | 접근축오차 | 판정 |
|---|---|---|---|
| +8 cm | 0.92 mm | 0.33° | 수렴 |
| +10 cm | 7.14 mm | 3.75° | **관절한계 접촉** |
| +12 cm | 19.9 mm | 11.2° | **실패** |

12cm 로 두면 IK 가 **관절한계에 클램프된 해**를 내고, 그리퍼가 기울어진 채 올라간다.
물체는 올라간다. 성공 판정도 통과한다. **요청한 자세가 아닌데 성공으로 기록된다.**

이전에 보고한 "파지 20/20, 평균 상승 10.9cm" 가 이 경로로 나온 값이다.
`grasp_check` 이 들어올림 IK 의 **수렴 여부를 검사하지 않고** 결과만 썼다.

조치:
- `lift_height_m` → **0.08** (실측 수렴 한계)
- `GraspResult` 에 `lift_ik_converged` 추가, 미수렴 시행 수를 보고
- 재측정: **20/20 그대로, 평균 상승 7.0cm, 미수렴 0회**

성공률은 안 변했지만 이제 그 성공이 **요청한 자세로 얻은 것**이다.

어떻게 찾았나: replay baseline 이 0% 인 이유를 파다가, 기록된 궤적의 마지막 구간 자세가
이상한 것을 봤다. 결함 1을 고친 뒤라서 미수렴이 드러났다.

## 결함 5 — EXP_LOG 가 코드와 수치를 묶은 적이 한 번도 없었다

트래커의 존재 이유는 "이 수치가 어느 코드에서 나왔나"를 남기는 것이다.
그런데 기록된 **모든** 실행이 이랬다:

```json
{"git_rev": "unknown", "git_dirty": false}
```

원인 둘:

1. 계측은 MuJoCo 가 깔린 환경에서 도는데 그곳이 git 체크아웃이 아니었다
2. `git status --porcelain` 이 저장소 밖에서 **빈 출력**을 내고, 그 빈 출력을
   `bool("")` 로 읽어 **"clean"** 으로 판정했다. `git_dirty: false` 는
   "깨끗함"이 아니라 "저장소가 아님"이었다

조치 (`tracking/exp_log.py`):
- 저장소가 아니면 `git_dirty` 는 `None` 을 반환한다 (`git` 종료코드를 본다)
- `git_rev` 가 `unknown` 이면 **경고를 출력한다** — 조용히 낡지 않게
- `code_sha` 추가: 소스 트리 해시 (`sim/**` `policy/**` `configs/*.yaml` 등).
  git 없이도 수치를 코드에 묶는다

**남는 한계:** `code_sha` 는 커밋을 특정하지 못한다. `git_rev: unknown` 인 기록은
여전히 커밋으로 되짚어갈 수 없다. **근본 해결은 계측을 저장소 안에서 돌리는 것이다.**

어떻게 찾았나: README 의 수치 절을 자동 생성하려고 로그 필드를 훑다가
`git_rev` 가 전부 `unknown` 인 것을 봤다. **자동화가 데이터 품질 문제를 드러냈다.**

## 이 다섯 건에서 남는 규칙

1. **검사는 보정 전에 한다.** 클립·클램프·정규화 뒤에 검사하면 검사가 무의미해진다
2. **수치가 너무 깨끗하면 계측기를 의심한다.** 실패가 한 번도 안 나오는 것은 단서다
3. **문서에 적은 기준과 코드를 대조한다.** 둘이 다르면 문서가 아니라 코드가 실제다
4. **비교는 같은 조건에서만.** 시드가 다르면 비교가 아니다
5. **계측기가 정상인지 먼저 확인한다.** replay baseline 을 기록된 그 위치에서 먼저
   돌려본 것이 그것이다 — 0% 가 발견인지 고장인지 구분해야 한다
6. **"기록했다"는 "기록이 유용하다"와 다르다.** 필드가 채워져 있는지 실제로 읽어본다
