## ⭐ 이번 주 우선순위 (2026-09-09 정정)

**시뮬 환경은 이미 구축돼 있다.** MuJoCo 씬 · `configs/so101.yaml` · 데이터셋 v1~v5 ·

**"시뮬을 세팅"하는 작업이 아니다. 있는 것을 Ver1 로 갈아끼우는 작업이다.**

```
1순위  E. Ver1 그리퍼를 시뮬에 반영 + 재수집        ← 일주일이 꽉 찬다. 막힌 것 없음
2순위  C. VLM 파인튜닝 (더미 라벨 루프까지)         ← GPU 대기 시간에 병행
3순위  A. 위상 waypoint 내보내기                    ← 반나절. 실물 투입은 비상정지 대기
4순위  B. 재라벨 A/B                                ← E 의 재수집에 실어 보내면 공짜
5순위  D. 잔차 std 3축 비교
```

**A 를 1순위에서 내린 이유**: 도구는 반나절이면 되는데 **결과물을 실물에 못 쓴다.**
물리 비상정지 수단이 아직 정해지지 않았다 (§5-1). 도구만 만들어두고 대기다.

### A. 위상 waypoint 내보내기 + 오프라인 검증 (3순위)

**왜**: 이게 되면 실물에서 첫 숫자를 잴 수 있다. 파이프라인 수정 0.

기록 에피소드 1편 → `MotionCommand` 5개(시작 + 위상 경계 4)로 변환하고,
인계본의 `core.models.validate_trajectory` 로 통과 여부를 검사하는 도구.

**이미 검증했다** 🟢 — 실측 위상별 이동량으로 계산해보니:

```
현행 (wrist_flex approach 85.7°)   → 거부  approach a_peak 5.998 > 3.0
시작자세 고침 (approach 0°)        → **통과**
  approach  v 0.404  a 1.036      descend  v 0.887  a 2.731 (91%)
  close     v 0.057  a 0.175      lift     v 0.683  a 1.402
```

**그리퍼 계단 명령 문제도 위상 waypoint 로 보내면 저절로 사라진다** (0.057 ≤ 0.08).

- 만들 곳: `AI/tools/export_waypoints.py` (`tools/` 는 provenance 해시 밖이다)
- 검증: 인계본 `validate_trajectory` 를 그대로 임포트. 고치지 마라
- 완료 기준: 98편 중 몇 편이 통과하는지 숫자로. `--start-pose-fix` 플래그로 두 조건 비교

### B. 재라벨 A/B — `action` 의미 결정 (계약 사안)

**공짜다.** 계약의 `state (6,)` 가 곧 측정된 관절 위치이므로
**`action_new[t] = state[t+1]`** 로 98편 전체를 **재수집 없이** 재라벨할 수 있다.

| 트랙 | `action` | RMS |
|---|---|---|
| 이 대화 | MuJoCo `ctrl` (명령) | 4.6987e-02 |
| UMI 변환 | `q[t+1]` (도달값) | 1.602e-02 |

**2.93배 차이인데 같은 `contract_version` 을 달고 있다** (L69). 황도경이 도달값으로
못박는 D-AI-35 초안을 냈고 **나도 동의한다** — 실물 API 가 도달값을 받고
(`Waypoint(positions_rad, gap_m, time_s)`), 재라벨이 공짜라 대기 비용이 0 이다.

- 재라벨 → 재학습 3시드 → 롤아웃. `ctrl` vs `q[t+1]` A/B
- **예측을 먼저 적어라** (황도경 예측: 게이트에서 구분 불가)
- 부수 이득: `action − state` 가 추종오차에서 **실제 이동량**으로 바뀐다

### C. VLM 파인튜닝 — 병행 (이슈 36 · 112 · 42)

**메인이 아니다.** 프로젝트 규칙: "UMI 모방학습이 메인스트림. VLM 과 시뮬레이션은
보조 도구다." 스코프가 커지면 자른다.

#### 이미 확정된 것 🟢

```
fp16 안전성 (실측)   Qwen2.5-VL-3B  argmax 일치 0.9909
                     SmolVLM2-500M  argmax 일치 0.9961     둘 다 통과
```

#### 지금 막혀 있는 것 ⚠️

**이슈 109(스킬 5종 확정 + 레지스트리 + VLM 출력 스키마)가 112 를 막고 있다.**
`skill_id` 값이 없으면 라벨 생성기가 무엇을 내야 할지 정할 수 없다.
**109 없이 라벨을 만들면 나중에 전부 다시 만든다.**

#### 109 없이 할 수 있는 것 — 이 순서로

1. **학습 루프를 더미 라벨로 먼저 완성한다.**
   프로젝트 규칙 그대로: "트랙 B 는 실데이터 없이 랜덤 텐서로 학습 루프를 먼저
   완성할 수 있다." LoRA 붙이고 한 스텝 도는 것까지. 라벨은 나중에 갈아끼운다.

2. **V100 제약을 먼저 확인한다** — 여기서 조용히 깨진다:

   ```
   bf16 실지원 X   ← Volta(sm_70). LoRA 학습에 bf16 쓰면 안 된다
   FlashAttention-2 X
   SDPA mem_efficient O
   ```

   **bf16 이 안 되므로 fp16 + GradScaler 를 써야 하고, fp16 LoRA 는 발산할 수 있다** 🟡.
   loss 가 NaN 이 되거나 조용히 스케일이 무너진다. **첫 실행에서 loss 곡선과
   grad scale 을 같이 로깅해라.** 이건 미검증이다 — 확인하면 LIMITS 에서 내린다.

3. **모델 하나로 좁힌다.** Jetson 제약이 **VLM + 정책 합쳐 8GB** 다.
   3B 와 500M 은 다른 세계다. **Jetson 이 4GB 인지 8GB 인지 아직 모른다** (§5-7).
   4GB 면 3B 는 논외다. → **HW 답이 오기 전에 3B 로 파인튜닝을 돌리지 마라.
   버려질 수 있다.** SmolVLM2-500M 으로 루프를 먼저 세우는 쪽이 안전하다 🟡.

4. **평가 기준을 먼저 못박는다.** 여기도 val loss 함정이 그대로 적용된다 —
   VLM 의 판정 지표는 **스킬 분류 정확도(또는 출력 스키마 준수율)** 이지
   학습 손실이 아니다. 게이트 숫자를 결과 보기 전에 정해라.

#### 하면 안 되는 것

- 109 확정 전에 **라벨 대량 생성** — 스키마가 바뀌면 전량 폐기다
- Jetson 용량 답 전에 **3B 파인튜닝 장시간 실행** — GPU 낭비 위험
- VLM 성능을 올리려고 정책 쪽 시간을 쓰는 것 — 보조 도구다

| 항목 | 내용 | 근거 |
|---|---|---|

### 30Hz 문제의 정체 — 리샘플러 파라미터가 아니다

```python
# 인계본 core/models.py:91
if 1.875*delta/dt > max_speed or 5.774*delta/dt**2 > max_accel:
```

`Δq = v·dt` 를 대입하면 검사값이 `5.774·v/dt` 다 — **dt 가 작을수록 나쁘게 판정된다.**
30Hz 를 만족하려면 관절 속도가 **0.99 °/s** 여야 한다 (우리 시연은 78.1 °/s, 79배).
에피소드 하나가 6.2분이 된다.

**원인은 검사식이 아니라 실행기다** — `control.py:77` 이 waypoint 쌍마다
quintic 정지→정지(`smooth=True`)를 실제로 적용한다. 5.774 는 **정확한 계수**다.
30Hz 스트림은 초당 30번 정지·재출발한다.

→ **"검사식만 고치자"는 위험하다.** 검사가 통과시키고 실행기는 5.774배로 돌린다.
실행기가 연속 보간(C¹)을 갖거나, 아니면 waypoint 를 성기게 보내야 한다.

→ **그래서 §2-A 가 중요하다. 시연 재생은 위상 waypoint 로 지금 된다.
정책 실행만 이 문제에 걸린다.**
