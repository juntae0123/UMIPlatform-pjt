## 1. 조용히 틀리는 값 4개 — 최우선

이 넷은 **에러를 내지 않는다.** 잘못된 값으로도 코드가 정상 실행되고 팔만 엉뚱하게
움직인다. 이 프로젝트에서 가장 비싼 실패 경로다.

### 1-1. `direction` 부호 — 관절 6개 전부 ⚠️⚠️ 1순위

```json
"shoulder_pan":  {"direction": 1}   ...  전 관절 direction=1
notes: "direction=1 and 0..4095 are placeholders, NOT physical direction"
```

**완료 기준**: 관절 6개 각각 — tick 을 **증가**시켰을 때 팔이 어느 쪽으로 도는가.
`+1`(모델과 같은 방향) 또는 `-1`(반대) 로 답해 달라.

**틀리면 무슨 일이 나나**: 부호가 반대인 관절이 있으면 궤적이 그 관절에서 거울처럼
뒤집힌다. 안전검사는 통과한다 — 검사기는 모델 좌표로 계산하고 실물이 반대로 도는 걸
모른다. **팔이 책상이나 자기 몸통으로 들어갈 수 있다.**

**측정 방법 제안**: 토크 켠 상태에서 관절 하나만 `zero_tick + 100` 으로 보내고
눈으로 방향 확인. 100 tick = 8.8°. 나머지는 고정.

---

### 1-2. `shoulder_lift` 영점 — 2200 인가 2048 인가 ⚠️⚠️ 2순위

```json
"shoulder_lift": {"zero_tick": 2200}
notes: "Shoulder lift 2200 is the active targets value; commented alternative is 2048.
        Zero-pose meaning requires confirmation."
```

두 값의 차이:

```
2200 − 2048 = 152 tick
             = 152 × (2π/4096) = 0.23317 rad = 13.359°
0.3m 리치에서 손끝 위치로  →  69.3 mm
```

**AI 실측 재생 허용오차 🟢: ±10mm 에서 3/4 · ±15mm 에서 1/4 · ±50mm 에서 0/4.**
**69mm 는 그것의 7배다.** 그리고 이건 랜덤 노이즈가 아니라 **상수 편향**이라
학습으로 지워지지 않는다 — 궤적 전체를 통째로 민다.

**완료 기준**: 모델의 `shoulder_lift = 0 rad` 자세가 실물에서 어떤 자세인가.
그 자세에서 서보가 읽는 tick 값 하나.

**참고 — 나머지 관절의 영점도 서로 다르다**: pan 1990 · elbow 2048 ·
wrist_flex 2048 · wrist_roll 2126. 2048 이 아닌 것(1990, 2126, 2200)은
장착 오프셋 보정으로 보이는데 **어떻게 정한 값인지** 알려 달라 (실측 / 계산 / 추정).

---

### 1-3. 모터 ID 교환 계획 ⚠️ 3순위

```
현재  Gripper = ID 5 · Wrist Roll = ID 6
README: "Gripper ID 5와 Wrist Roll ID 6의 교환 계획은 아직 적용되지 않았다."
```

**완료 기준**: 교환할 계획인가? 한다면 **언제**, 그리고 `jetson/jetson_config.json` 을
**누가** 고치는가.

**틀리면 무슨 일이 나나**: 교환하고 설정을 안 고치면 **그리퍼를 닫으라는 명령이
손목을 돌린다.** 그 반대도 마찬가지다. 안전검사는 통과한다.

가능하면 **교환하지 않는 쪽**을 권한다 — 지금 설정이 현재 배선과 맞고, 바꿔서
얻는 게 이름 순서뿐이라면 리스크만 남는다. 꼭 바꿔야 하는 이유가 있으면 알려 달라.

---

### 1-4. `min_tick` / `max_tick` 실측 ⚠️ 4순위

```json
"min_tick": 0, "max_tick": 4095      전 관절
notes: "0..4095 are placeholders, NOT calibrated limits"
```

**완료 기준**: 관절별로 **물리적으로 부딪히기 전까지** 갈 수 있는 tick 최소·최대.

**왜 소프트 리밋으로 충분하지 않나**: `limits_rad` 는 모델 좌표의 소프트 리밋이고,
그 변환이 `zero_tick`·`direction` 에 의존한다. §1-1 이나 §1-2 가 틀리면
**소프트 리밋을 지키면서도 하드 리밋을 넘을 수 있다.** tick 한계는 그 경우의
마지막 방어선이다. 지금은 방어선이 없다 (0~4095 = 전 범위 허용).

## 2. 속도·가속도 — 값의 **출처**가 필요하다

받은 값:

```
so101_ver1.json      max_speed_rad_s 1.0  (= 57.30 °/s)
                     max_accel_rad_s2 3.0
                     max_gap_speed_m_s 0.08 · max_gap_accel_m_s2 0.3
jetson_config.json   speed_tick_s 300  (= 26.37 °/s)  · acceleration_register 10
```

**두 값이 2.17배 다르다.** `speed_tick_s 300` 이 더 빡빡하다.

**완료 기준** — 각 값에 대해 하나만 골라 달라:

| | 🟢 실측 | 🔵 데이터시트 | 🟡 선택한 보수값 |
|---|---|---|---|
| `max_speed_rad_s 1.0` | | | |
| `max_accel_rad_s2 3.0` | | | |
| `speed_tick_s 300` | | | |

그리고 **올릴 수 있는가**. STS3215 의 무부하 최대 속도와, 우리 페이로드(20g)에서
실제로 낼 수 있는 속도.

**왜 이게 중요한가**: AI 가 실측한 사람 UMI 시연의 각속도가 **최대 53.6 °/s** 다.

```
max_speed 1.0 (57.30 °/s) 대비   93.6%   ← 간신히 아래
speed_tick_s 300 (26.37 °/s) 대비  2.03배 초과
```

**사람 시연 속도가 로봇 한계의 90%대라는 건 여유가 거의 없다는 뜻이다.**
`speed_tick_s` 를 못 올리면 시연을 느리게 다시 찍거나 재표집해야 한다.

### 2-1. 아직 아무 데도 없는 값

| 항목 | 왜 필요한가 |
|---|---|
| **실제 스톨 토크** (N·m) | MJCF `forcerange ±3.35` 는 시뮬 값이다. 실물 값이 아니다 |
| **과열 컷오프** | 있음/없음. 있으면 조건. 반복 학습 롤아웃을 돌리면 걸린다 |
| **과전류 보호** | 같음 |
| **전원 사양** | 전압·최대 전류. 6축 동시 구동 시 전원이 버티는가 |

## 3. 그리퍼 — 두 질문

### 3-1. **Ver1 이 최종인가?** ⚠️ 이 답에 데이터셋 재수집이 걸려 있다

인계본의 Ver1 은 공식 SO-101 그리퍼와 **완전히 다른 기구**다.

```
공식 (AI 시뮬 현행)   hinge 관절, [-0.1745, 1.7453] rad, moving_jaw_so101_v1.stl
Ver1  (실물)          slide 관절, 편측 0~0.045 m (gap 0~0.09 m)
                      finger_left/right · pinion · drive_motor · holder · adapter
                      pinion_passive = -55.5556 × q
```

**완료 기준**: Ver1 이 출품까지 갈 최종 형상인가, 아니면 더 바뀌는가.

**AI 쪽 영향**: 시뮬을 Ver1 로 바꾸면 **수집한 98편과 학습된 체크포인트 전부가
무효**가 된다 (이미지·접촉 동역학이 바뀐다). 그 재수집을 **한 번만** 하고 싶다.
더 바뀔 예정이면 지금 안 바꾸고 기다리는 게 맞다.

### 3-2. tick ↔ 실측 간격 곡선

```json
"gripper": {"closed_tick": 1720, "open_tick": 70, "min_tick": 70, "max_tick": 1720}
notes: "User confirmed closed_tick=1720. open_tick=70 is inferred from the 70..1720
        comment; physical gap unverified."
```

**완료 기준**: 최소 5점.

| tick | 실측 손가락 간격 (mm) |
|---|---|
| 1720 (완전 닫힘) | ? — 0 인가, 아니면 패드가 닿아서 그 이상인가 |
| 1300 | ? |
| 900 | ? |
| 500 | ? |
| 70 (완전 열림) | ? — 90mm 가 맞는가 |

**측정 지점을 병기해 달라** (손가락 팁 / 패드 중앙). AI 시뮬은 **패드 간격** 기준으로
실측 곡선을 갖고 있어서, 지점이 다르면 두 곡선을 이을 수 없다.

**AI 쪽 참고 🟢**: 시뮬 `gap_curve` 는 5.3 ~ 79.4 mm 다. Ver1 은 0 ~ 90 mm.
**Ver1 의 0~90mm 가 MW 핸드헬드 캘리브레이션 0~90mm 와 정확히 같다** — 핸드헬드가
공식 그리퍼가 아니라 Ver1 기준으로 만들어진 것으로 보인다. 이것도 확인 부탁한다.

## 4. 카메라 — 인계본에 아예 없다

Ver1 이 손목 조립을 통째로 교체했다. 공식 MJCF 기준으로 잡아둔 손목 카메라 위치가
그대로 유효한지 알 수 없다.

**완료 기준 4개**:

1. **손목 카메라가 Ver1 의 어느 부품에 붙는가** — `adapter` / `holder` / `cover_top` 중 어디
2. **손목 카메라 렌즈 중심 → 손가락 끝 거리** (mm) — 값 하나
3. **정면 카메라** 위치(x,y,z)와 바라보는 방향. 베이스 기준. 대략값도 도움된다
4. **탈착 반복성** — 떼고 다시 붙이면 같은 자리인가. 나사 구멍이 위치를 정하는가

**2번이 왜 값 하나로 중요한가** (LIMITS L60): UMI 핸드헬드 핑거가 SO-101 의
**50% 축소**다. UMI 가 캘리브레이션 없이 성립하는 근거는 **손목 카메라에 찍히는
핑거의 겉보기 크기가 일치**하는 것이다. 카메라→핑거끝 거리도 절반이어야 상쇄된다.
**비가 0.5 에서 멀면 학습은 잘 되고 실물에서만 실패한다.** 시뮬에서 절대 안 보인다.

참고: 인계본에 TCP 가 정의돼 있다 — `gripper_tcp` = `custom_hand` 기준
`[0, -0.0780187530518, 0.0270000119209] m` (원점에서 82.56mm). 카메라 마운트
위치를 주면 AI 가 거리를 계산할 수 있다.

**4번이 왜 중요한가** 🟢: hand-eye 오차는 **상수 편향**이라 학습이 지우지 못한다.
실측 ±10mm 에서 재생 성공률이 4/4 → 3/4 로 떨어진다. 카메라가 매번 다른 자리에
붙으면 그 편향이 세션마다 달라지고, 그건 어떤 학습으로도 못 덮는다.

## 5. 제어 주기 — 계약 변경 여부가 걸려 있다

```python
# core/models.py
if not 0.05 <= dt <= 60:
    raise ValueError('waypoint duration must be 0.05..60 seconds')
```

```
파이프라인 최소 waypoint  0.05 s = 20 Hz
상태 폴링 poll_s          0.1 s  = 10 Hz
AI 데이터 계약            0.0333 s = 30 Hz   ← 거부된다
```

**완료 기준 2개**:

1. **명령**: 1Mbps UART 로 6축 sync write 를 **30Hz 로 보낼 수 있는가.**
   0.05초가 하드웨어 한계인가, 선택한 보수값인가
2. **상태 읽기**: 6축 위치를 **30Hz 로 읽을 수 있는가.** `poll_s 0.1` 이 한계인가 선택인가

**왜 중요한가**: AI 데이터 계약이 30Hz 관측·행동이다. 20Hz 나 10Hz 가 상한이면
**계약을 바꿔야 하고, 그러면 수집한 데이터가 무효가 된다.** 계약 변경은 양 트랙 합의와
결정기록이 필요한 사안이라 값을 먼저 알아야 한다.

30Hz 가 가능하다면 파이프라인 쪽에서 최소값을 낮추는 것만으로 해결된다 —
그게 가장 싼 경로다.

## 6. 실물 실행의 전제 — 아직 정해지지 않은 것

### 6-1. 물리 비상정지 수단

```
README: "이 모듈은 토크를 자동으로 켜거나 끄지 않는다. 토크 해제 시 로봇이
        떨어질 수 있으므로 담당 애플리케이션에서 물리 비상정지 방식과 함께
        정책을 정한다."
```

**완료 기준**: 손으로 즉시 끊을 수 있는 수단이 무엇인가 (전원 스위치 / 물리 버튼 /
UART 뽑기). 그리고 **끊었을 때 팔이 떨어지는가.**

**AI 쪽 사정**: 실물에서 개루프 재생조차 이게 정해지기 전에는 못 한다.
떨어지는 구조면 저자세에서만 시작하는 식으로 절차를 짜야 한다.

### 6-2. 책상·클램프 치수

```
so101_ver1.json notes: "Table corner not measured: conservative infinite working
                        plane at base underside."
collision_reviewed: false
```

**완료 기준**: 책상 상판 크기, 베이스가 클램프된 위치(모서리에서 얼마), 상판 높이.

AI 시뮬은 `task.table` 로 책상을 두고 있고 작업영역을
`x [0.10, 0.25] · y [-0.175, 0.175]` (도달 63.9%, 최대 연속 15×35cm) 로 실측했다.
실제 책상에서 그 영역이 확보되는지 대조해야 한다.

### 6-3. Jetson 모델

```
README: "인터넷과 TLS를 사용할 수 없는 기존 Jetson"
포트: /dev/ttyTHS1
```

**완료 기준**: 정확한 모델명과 **메모리 4GB 인가 8GB 인가**.

이슈 42 가 "VLM + 정책 합쳐 8GB" 제약으로 스코프를 잡고 있는데, 실제가 4GB 면
VLM 스코프를 다시 잘라야 한다. 그리고 인터넷이 없으면 모델 가중치 배포 경로도
따로 짜야 한다 (BE 와 협의 사항).
