## 두 경로는 검사식이 다르다 — 합치지 않는다

| 경로 | 검사 | 확신도 |

## 반드시 알아야 할 구조적 사실

**ROS2 검사는 위치와 tick 만 본다.** 같은 궤적을 느리게 보내든 waypoint 를 솎든
**같은 위치를 지나므로 통과율이 바뀌지 않는다.**

→ **ROS2 가 실패하면 시간 스케일링은 처방이 아니다.** 남는 처방은 궤적이 지나는
위치를 바꾸는 것이고, 그 최소 개입이 **URDF 한계로의 클램프**다. 그래서 패스 B 가 있다.

## 측정 설계 — 한 번의 롤아웃 예산, 여러 판정

롤아웃은 결정적이다 🟢 (2026-09-10 `eval_rollout` 2회 완전 동일). 명령열을 한 번 모으면
그 뒤 판정은 재롤아웃 없이 후처리로 나온다.

| 패스 | 무엇 | 비용 |
|---|---|---|
| **A** | 정책 그대로. 명령열·최근접 틱 수집 + **기존 성공률 재현 fixture** | n |
| **B** (`--clamp-pass`) | 팔 명령을 URDF 한계로 클램프. **처방 후보 검증** | n |

| 후처리 | ROS2 판정 · direct 판정 · 시간 스케일링 k∈{1,1.5,2,3,5,10,20,30} | 0 |

## 사전등록 판정 (결과 보기 전 확정)

**주 판정은 ROS2 에피소드 통과율이다.**

| ROS2 통과율 | 판정 | 다음 |
|---|---|---|
| >= 80% | `ros2_ok__pick_execution_path` | 실행 경로를 ROS2 로 확정하고 추종성 계측으로 |
| 30~80% | `ros2_partial__align_config_or_change_trajectory` | 패스 B 결과로 처방 결정 |
| < 30% | `ros2_blocked__config_or_ros_hw_agreement_first` | 정책 학습보다 config·실행 계층 합의가 먼저 |

**보조 판정 (전부 결과 전 확정)**

1. `elbow_flex.position_lower` 가 ROS2 위반의 **과반**이면 → 원인은 **config 불일치**다
   (URDF −1.5708 vs 우리 −1.69). 정책 문제가 아니다
2. 패스 B 성공률이 A 대비 **−5%p 이내**면 → **클램프가 처방이다.** config 정합만으로 끝난다
3. 패스 B 성공률이 A 대비 **−15%p 이상** 떨어지면 → 정책이 그 영역을 실제로 필요로 한다.
   config 를 넓히도록 HW 와 합의하거나 태스크·씬을 바꿔야 한다
4. `scripted` 도 ROS2 통과율 80% 미만이면 → **정책 고유 문제가 아니다.** 태스크·config 문제
5. direct 통과율이 낮고 ROS2 가 높으면 → **두 실행 경로의 차이**이지 정책 성능 문제가 아니다
6. 패스 C 가 A 대비 **+15%p 이상**이면 → 폐쇄 시각을 관측으로 맞히는 데 투자할 값이 있다.
   **+5%p 미만이면 병목은 시각이 아니라 팔이다**

## 예측 (실행 전에 적는다) 🟡

- **ROS2 통과율 30~70%** 사이. `elbow_flex` 하한이 위반의 과반을 차지한다
- **패스 B 는 A 대비 −5%p 이내.** 초과량이 경계 근처(수 도)일 것이므로 클램프해도
  성공률이 거의 안 떨어진다 → 처방은 config 정합
- **direct 통과율 x1 에서 0%.** 30Hz 의 `dt=0.0333s` 가 최소 waypoint 0.05s 보다 작다.
  통과 시작은 **k>=1.5** 부터
- **패스 C 는 A 대비 +5~20%p.** DAgger 는 닫는 순간이 이미 4.9mm 라 여지가 작고,
  v5 는 25.6mm 라 여지가 크다
- `scripted` 는 ROS2 통과율 80% 이상

**크게 빗나갈 때의 뜻**: 패스 B 가 −15%p 이상이면 "우리 config 가 그냥 넓다"는 내 해석이
틀린 것이고, 정책이 URDF 밖 영역을 실제로 쓰고 있다는 뜻이다. 그러면 config 정합이
아니라 **태스크·씬 재설계**가 후보가 된다.

## 해석 제한

- **명령점 검사다.** `JointTrajectoryController` 는 30Hz 로 보간점을 내고 하드웨어
  인터페이스는 그 보간점을 검사한다. 여기서는 정책 샘플 명령만 본다 →
  **ROS2 통과율은 하한이다.** 통과해도 보간점이 걸릴 수 있다
- 실물 추종 오차(`tracking_rad 0.08`·`tracking_gap_m 0.004`)를 재지 않는다. 실물 로그가 없다
- 패스 C 는 미래를 보는 조건이다. **배포 처방이 아니라 상한 계측기다**
- 충돌·설치·영점 재검증·비상정지를 다루지 않는다
- `real_calibration_verified`·`installation_verified`·`collision_reviewed` 가 전부 `false` 다.
  **어떤 결과도 실물 안전 승인이 아니다.** 통과는 "설정상 명령열 한계 통과" 까지만 뜻한다
- 체크포인트 3개다. 학습 실행 간 성공률 25%p 편차 실측이 있다 🟢
