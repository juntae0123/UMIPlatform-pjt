## D-AI-30 · 조건 비교의 표준 블록을 **학습 5회**로 올린다

작성자: 김준태(트랙B) · 2026-09-07 · 관련 이슈 S15P21A103-34, S15P21A103-35
합의: 트랙 A ☐ / 트랙 B ☐

**배경**

`contract/skills.py` 의 `GATE_MIN_RUNS = 3` 으로 지금까지 모든 조건을 비교했고,
합산 이항 구간(n=300)으로 "겹친다 / 갈라진다"를 판정했다. 그 합산이 틀렸다.
롤아웃끼리 정책을 공유하고, 3회 실행이 평가 시드 블록까지 공유한다. 독립 300 이 아니다.

**실행 수준으로 보면 3회는 구조적으로 부족하다** 🟢

3 vs 3 의 순열검정에서 가능한 배치는 C(6,3) = 20 가지이므로 **최소 단측 p 는
1/20 = 0.05** 다. 즉 어떤 3회 실험도 경계선을 넘을 수 없다.
실제로 v4(0, 0, 0) vs v5(2, 12, 14) — 지금까지 가장 큰 효과 — 가 정확히 p = 0.05 다.

5회면 C(10,5) = 252 → 최소 단측 p 는 0.004 다.

**결정**

| 목적 | 실행 수 | 근거 |
|---|---|---|
| "학습이 망가지지 않았나" 확인 | **3회 유지** | 총체적 고장 검출에는 충분하다 |
| **조건 A vs 조건 B 비교** | **5회** | 실행 수준 검정이 경계선을 벗어나는 최소값 |
| 배포 게이트 판정 | 5회 + n≥100 | 위와 같음 |

평가 시드 블록은 3000~3099 로 **유지**한다 (모든 조건이 같은 물체 배치를 본다).
비교는 같은 시드의 성공/실패 차이를 쓰는 **paired** 로 하고, 구간은 학습 실행을
군집으로 보는 부트스트랩으로 낸다.

**이것은 게이트 완화가 아니다**

`ROLLOUT_GATE = 0.20` 은 건드리지 않는다. 게이트를 옮기는 것은 사후 합리화이고
n 을 올리는 것은 정밀도 개선이다. 이 결정은 후자다.

**비용** 🟢

학습 1회 1332초(V100 1장, 44.4초/epoch × 30). 5회 = 111분.
GPU 10장이고 PCIe 라 GPU당 독립 잡이 맞으므로 **5장에 뿌리면 벽시계 22분**이다.
3회에서 5회로 가는 비용은 실질적으로 0 이다.

**보정 (같은 날, 외부 검토 반영)**

5회는 **최소 규격이고 충분성 보장이 아니다.** C(10,5)=252 는 최소 가능 p 이고
검정력·구간 폭은 다른 문제다. v3·v5 의 실행 값이 1~14% 로 흩어져 있으므로
5개로도 구간이 넓을 수 있다.

비용을 다시 계산하면 결론이 바뀐다 🟢 — 학습 1회 22분, V100 **10장**, PCIe 라
GPU당 독립 잡이 맞다.

⚠️ **정정 2회 (같은 날).** 두 번 틀렸다.

1차 정정: GPU 10장 독점 가정이 틀렸다 (공유 서버). "동시 2~3장" 으로 고쳤다.
2차 정정: **그것도 틀렸다.** SSAFY 원칙은 **GPU 한 장 할당**이다. 사용자가
알려줬고, 실제로 서버 측에서 "풀로 쓰고 있다, 킬하겠다" 경고를 받았다.
내가 `CUDA_VISIBLE_DEVICES=1` 로 두 번째 장을 잡은 것이 그 원인 중 하나다.

**현실 예산: 동시 1장, 잡 1개.** 학습 1회 22분이므로

| 실행 수 | 벽시계 (순차, 1장) |
|---|---|
| 3 | 약 1.1시간 |
| 5 | 약 1.8시간 |
| 10 | 약 3.7시간 |

10시드는 casual 하게 돌릴 수 있는 것이 아니다. **최종 후보에만 쓰고, 야간에
돌린다.** 탐색은 5시드로 하고, 그것도 1.8시간이므로 조건 수를 먼저 줄인다.

**병렬로 여러 조건을 훑는 계획은 폐기한다** — "GPU 유휴분에 던져둔다" 같은
지시를 내가 여러 번 냈는데, 유휴분은 내 것이 아니다.

그리고 **스레드 캡을 반드시 씌운다** 🟢 — 프로세스마다 BLAS 스레드를 코어
수만큼(80) 띄우기 때문에 6개 프로세스에서 load average 165/80 이 나왔다.
이 작업들(1.3M 파라미터, 단일 물체 MuJoCo)은 스레드가 많아서 빨라지지 않고
**남의 작업만 느려진다.**

```
OMP_NUM_THREADS=2 MKL_NUM_THREADS=2 OPENBLAS_NUM_THREADS=2 CUDA_VISIBLE_DEVICES=<한 장>
```

착수 전에 `nvidia-smi --query-compute-apps=...` 와 `w` 로 **남이 쓰는 것을 먼저
확인한다.**

| 용도 | 실행 수 | 벽시계 (1장 순차) |
|---|---|---|
| "학습이 망가졌나" 확인 | 3 | 약 1.1시간 |
| 탐색 (조건 하나) | 5 | 약 1.8시간 |
| **최종 후보** (Z1 · old-expert 400 · DAgger 400) | **10** | 약 3.7시간 · **야간** |

5개로 판정이 안 되면 **모든 조건을 동일하게** 10개로 확대한다.
유리해 보이는 조건만 추가 실행하지 않는다 — 그건 선택 편향이다.

**되돌릴 조건**

- 실행 편차(L40, 현재 12%p)가 5%p 이하로 줄면 5회로 되돌릴 수 있다
- 10회에서도 판정이 안 되면 게이트를 옮기지 말고 **평가 n 을 올린다**

**파급**

- `contract/skills.py` `GATE_MIN_RUNS` — 상수 하나. 코드 변경 필요
- 이미 3회로 기록된 v2·v3·v4·v5·v6 판정은 **"경계선"으로 재표기**한다.
  소급 폐기는 하지 않는다 (기록에 없는 과거를 만들지 않는다)
- 트랙 A 의 도메인 랜덤화 붕괴율(D-AI-18)도 같은 문제를 갖는다 — **확인 필요**

## D-AI-31 · 조건 비교 실행은 **커밋된 트리에서만** 한다

작성자: 김준태(트랙B) · 2026-09-07 · 관련 이슈 S15P21A103-34
합의: 트랙 A ☐ / 트랙 B ☐

**배경** 🟢

`EXP_LOG.jsonl` 의 `repeat_runs` 5건이 **전부** `dirty=True` 였고 `code_sha` 와
`config_sha` 가 매번 달랐다. v3 과 v5 는 데이터가 바이트 단위로 동일한데
성공률이 4.3% vs 9.3% 다. 차이는 코드·config 인데 **여러 개가 동시에 바뀌었고
커밋으로 되짚어갈 수 없다.** 그래서 어느 변경에도 귀속시킬 수 없다.

추가로 `log_run` 이 `git_rev`·`code_sha` 를 **로그 시점에** 계산한다. 몇 시간 도는
잡에서는 그 트리가 수치를 만든 트리가 아니다 — v6 이 잡 시작 시점에 없던 커밋을
자기 리비전으로 기록했다.

**결정**

1. **조건 비교가 목적인 실행은 커밋 후에만 시작한다.** 더러운 트리에서 나온 수치는
   비교 대상이 아니라 참고값으로 기록한다
2. 계측 도구는 **실행 시작 시점**의 `code_sha` 를 조건에 함께 남긴다
   (`eval/repeat.py` 의 `CODE_SHA_AT_LAUNCH`. 다른 도구는 미적용 — L45)
3. 한 실행에서 바꾸는 요인은 **하나**로 제한한다. 여러 개를 바꿔야 하면 각각을
   별도 실행으로 쪼갠다

**되돌릴 조건**

없다. 이건 취향이 아니라 귀속 가능성의 최소 조건이다.
다만 (3) 은 탐색 단계에서는 완화할 수 있다 — 그때는 결과를 "탐색"으로 표기하고
게이트 판정에 쓰지 않는다.

**파급**

- `eval/repeat.py` 실행 전 경고 추가됨 (커밋 `4a6fb2a`)
- 다른 계측 도구 미적용 → L45

## D-AI-32 · 이 라운드의 **종료 조건과 다음 모델 선택**을 미리 정한다

작성자: 김준태(트랙B) · 2026-09-07 · 관련 이슈 S15P21A103-34
합의: 트랙 A ☐ / 트랙 B ☐

**배경**

"이번 라운드가 다 겹치면 ACT 로 전환"이라는 규칙을 검토받았고, **너무 강하다는
지적이 맞다.** 전부 실패하는 원인이 여러 개일 수 있고 (한 스텝 정확도, 부분관측성,
파지 후 고정점, 전문가 품질, 데이터량, 인코더, 행동 horizon) 실패 사실만으로는
어느 모델로 갈지 정해지지 않는다.

**결정**

BC 계열의 어떤 개입도 게이트 20% 를 넘지 못하면 **미세 조정을 중단하고**,
P0~P1 진단이 지목한 실패 기전에 따라 다음 모델을 **사전 선택된 표에서** 고른다.

| 진단 결과 | 다음 모델 |
|---|---|
| kick 성공 + 포화-정지 창에서 관측 충돌 | history 또는 action chunking |
| 위상/이력 진단만 개선 | recurrent / history 모델 |
| A′ 도 실패 (분포 내 오차만으로 실패) | 한 스텝 정확도 · 행동 표현 · 모델 용량 |
| offline 400 이 개선 | 그냥 BC 스케일링 계속 |
| DAgger 만 개선 | on-policy aggregation |
| 고주파 행동 부호 전환이 실패와 연관 | ACT / chunking |

**어느 칸도 지목되지 않으면** 개입을 더 추가하지 않고 진단을 더 한다.
"뭘 해도 안 되니 큰 모델로" 는 이 표에 없다.

**되돌릴 조건**

진단이 두 칸 이상을 동시에 지목하면 표를 다시 만든다. 그때는 지목된 기전들의
비중(실패 전수 분류의 분포)으로 순서를 정한다.

## 폐기 · 상관 argmax 로 페어링을 판정하려던 것

작성자: 김준태(트랙B) · 2026-09-07

`action_t − state_t` 와 `state_{t+k} − state_t` 의 상관 argmax 로 obs/action 페어링
off-by-one 을 판정하려 했다. **폐기한다.**

내가 처음 쓴 판정("argmax k = 1 이어야 한다")은 위치 제어 지연 때문에 틀렸고,
그걸 고친 판정("argmax k ≤ 0 이면 버그")도 안전하지 않다 — **scripted 행동이
부드럽고 자기상관이 크므로 페어링이 틀려도 k=1~3 에서 비슷한 상관이 나온다.**
(k=0 항이 항등적으로 0 이라는 지적도 있었으나, 음수 k 는 정의되므로 그건 부분적
이유다. 결정적 이유는 자기상관이다.)

**대체 — sentinel action 수집 검사.** 학습 없이 짧은 캘리브레이션 에피소드 하나를
만들고, 관절별로 구분 가능한 **비주기 펄스**를 action 에 넣는다. 수집 루프 안에서
pre-step 관측 tick ID · `env.step` 에 넘긴 action 의 tick ID · post-step 관측 tick ID ·
dataset builder 가 저장한 인덱스를 직접 기록하고 assert 한다.

판정: 저장 인덱스가 수집 루프의 tick ID 와 다르면 **버그 확정.**
코드상 쌍이 맞고 펄스의 최초 물리 반응이 post-step 관측부터 나타나면 통과.
반응이 2~3틱 뒤에 커지는 것은 actuator 동역학이고 페어링 오류가 아니다.

상관 그래프는 보조 플롯으로만 남긴다. 판정기로 쓰지 않는다.
